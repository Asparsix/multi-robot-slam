\begin{abstract}
We run four robots in one house and ask them to visit a list of places
(tasks) without crashing into walls or into each other. This note explains
the idea end-to-end for a non-research audience: what each step is for, what
goes in, what comes out, and how the steps connect. No equations, no
pseudocode --- just the story of the system.
\end{abstract}

\section{The problem in one sentence}
%------------------------------------------------------------------------------

\textbf{Four robots share one house. There are ten places they must visit.
Split the work fairly, move without hitting each other, and finish every
place.}

If only one robot existed, this would be ``go from A to B.'' With four robots
and many goals, we need extra layers: a shared map, task assignment, and
traffic planning so they do not block or bump into each other.

%------------------------------------------------------------------------------

\textbf{Important:} ``Navigation'' in the everyday sense (drive to a point) is
mostly step~5. Steps~1--4 exist so that driving is smart for a \emph{team}.

Often we build the map once (step~1), save it, and then reuse it. Steps~2--5
run every mission. Steps~4--5 repeat for each next goal in the robots' lists.

%------------------------------------------------------------------------------
\section{Step 1 --- Multi-robot SLAM (build the map)}
%------------------------------------------------------------------------------

\subsection{What problem this solves}

The robots do not magically know the house layout. They need a map: where
walls are, where free space is. Without that, they cannot plan routes or
agree on ``task T04 is here.''

\subsection{What SLAM means in plain words}

\textbf{SLAM} = build a map \emph{while} figuring out where you are on that
map. The robot looks around with a laser (LIDAR), moves a bit using wheel
odometry, and glues scans together into one picture of the rooms.

A useful mental model: the robot keeps many guesses (``I might be here, or
here, or here''). New laser readings make some guesses more believable. Over
time the map fills in and the best guess of the robot's position settles.

\subsection{Why \emph{multi}-robot SLAM}

One robot mapping the whole house is slow. Four robots explore different
rooms and share what they see. The result we want is \textbf{one shared map},
not four private sketches. Later, when we say ``go to the kitchen,'' every
robot means the same place.

\subsection{What we take away from this step}

A floor-plan style grid: free cells vs walls. For demos we often save that map
and reload it, so we do not remake the house every run.

\textbf{This step does not assign tasks and does not stop robots from
colliding with each other during the mission.} It only answers: \emph{what
does the world look like?}

%------------------------------------------------------------------------------
\section{Step 2 --- Localization (where is each robot?)}
%------------------------------------------------------------------------------

\subsection{What problem this solves}

Once the map exists, each robot still needs a live answer: ``I am at this
spot, facing this way.'' That is localization.

\subsection{How to think about it}

Again, particle-style thinking helps: many possible positions; laser scans
vote for the ones that match the known map; the robot reports the best
estimate. Wheel motion updates the guess between scans.

\subsection{Why we need it before anything else in the mission}

\begin{itemize}[leftmargin=*]
  \item Task assignment needs to know who is already close to which goals.
  \item Path planning needs a start point for every robot.
  \item Finishing a task means checking ``did I actually arrive?''
\end{itemize}

Without localization, goals are just numbers on paper.

%------------------------------------------------------------------------------
\section{Step 3 --- CBBA (who does which tasks?)}
%------------------------------------------------------------------------------

\subsection{What problem this solves}

We have ten places to visit and four robots. If everyone rushes to the
nearest goal, they fight over the same jobs and leave others untouched. We
need a fair, sensible split: \textbf{which robot takes which tasks, and in
what order.}

\subsection{What CBBA is (high level)}

\textbf{CBBA} is an auction-style assignment method. Each robot builds a short
\textbf{to-do list} (a ``bundle'') of tasks. Robots ``bid'' on tasks. Through a
few rounds of sharing bids, they agree so that each task has at most one
owner.

\subsection{How bidding works (intuition, not formulas)}

A robot does not only ask ``is this task close to me?'' It asks:

\begin{quote}
\emph{If I add this task into my current to-do list in the best place, how much
extra travel does that cost me?}
\end{quote}

That ``extra effort'' idea is the \textbf{marginal cost} idea. A task that sits
naturally on your route is cheap to add; a task that forces a long detour is
expensive. Robots that can serve a task with less extra effort tend to win it.

To estimate travel, we look at a path on the map that goes around walls (not
just a straight line through furniture). If that lookup is busy or fails, we
fall back to straight-line distance as a rough guess.

\subsection{What CBBA does \emph{not} do}

CBBA does \textbf{not} drive the robots. After CBBA finishes, we only have
ordered lists like:

\begin{itemize}[leftmargin=*]
  \item Robot 1: task A $\rightarrow$ task B $\rightarrow$ \ldots
  \item Robot 2: task C $\rightarrow$ task D $\rightarrow$ \ldots
\end{itemize}

We also limit how many tasks one robot may take in one auction round (bundle
size). Leftover tasks can be handed to robots afterward so all ten places
still get covered.

\subsection{How this feeds the next step}

We do not send a robot through its whole list at once. We go \textbf{leg by
leg}: everyone works on their ``next'' task; when that wave finishes, we take
the following task in each list. Each wave becomes a set of goals for path
planning.

%------------------------------------------------------------------------------
\section{Step 4 --- MAPF (plan so paths do not clash)}
%------------------------------------------------------------------------------

\subsection{What problem this solves}

Even with different goals, robots can meet in a doorway or corridor at the
same time. Individual ``go around walls'' planning is not enough --- we need
\textbf{team} planning: who is where at which time.

\subsection{What MAPF means}

\textbf{MAPF} = Multi-Agent Path Finding. Plan routes for everyone together so
that:
\begin{itemize}[leftmargin=*]
  \item two robots do not sit on the same spot at the same time, and
  \item they do not swap through each other on a narrow edge.
\end{itemize}
Waiting in place is allowed (``you pause while the other passes'').

\subsection{What people often hear: CBS / ECBS}

In research you will hear \textbf{CBS} or \textbf{ECBS} --- smarter methods that
search for conflicts and fix them carefully. Good to know as names.

\textbf{What we use instead:} a simpler idea called \textbf{prioritized
planning}.
\begin{enumerate}[leftmargin=*]
  \item Plan robot 1 first; ``reserve'' the cells it will use at each time.
  \item Plan robot 2 around those reservations (it may wait or take a detour).
  \item Same for robot 3, then robot 4.
\end{enumerate}

So paths are chosen so they \textbf{do not merge in a conflicting way in space
and time}. Lower-priority robots may wait longer --- that is the trade-off for
keeping the method simple and fast.

\subsection{Output}

For the current wave of goals, each robot gets a timed path: a sequence of
waypoints including ``stay here for a beat'' when needed.

%------------------------------------------------------------------------------
\section{Step 5 --- Execution (make the robots actually move)}
%------------------------------------------------------------------------------

\subsection{What problem this solves}

A plan on paper does not move wheels. Each robot still needs low-level
driving: follow the next pose, avoid local bumps, stop near the target.

\subsection{Why we do not ``just send the whole path''}

If every robot free-runs its full route on its own clock, they lose the
timing that MAPF carefully set. One arrives early, blocks a corridor, and the
team plan falls apart.

\subsection{What we do instead}

We treat the MAPF plan like a shared playlist of beats:
\begin{enumerate}[leftmargin=*]
  \item At beat $t$, every robot drives toward its pose for that beat.
  \item Wait until everyone is close enough (or time out).
  \item Advance to the next beat.
\end{enumerate}

So multi-robot planning stays in MAPF; single-robot driving only tracks the
current beat.

When the whole timed plan is done, we check which tasks were reached, then
start MAPF again for the next leg of the to-do lists.

%------------------------------------------------------------------------------
\section{Full story of one mission}
%------------------------------------------------------------------------------

\begin{enumerate}[leftmargin=*]
  \item \textbf{Map once:} robots explore (or we load a saved house map).
  \item \textbf{Bring everyone online:} each robot knows where it is on the map.
  \item \textbf{Assign work:} CBBA builds ordered to-do lists; attach leftovers
        if needed so all ten tasks are owned.
  \item \textbf{For each wave of ``next'' goals:}
        \begin{itemize}
          \item MAPF plans timed paths that do not clash.
          \item Robots drive beat-by-beat until that wave finishes.
          \item Check off completed tasks.
        \end{itemize}
  \item \textbf{Done} when every task place has been visited.
\end{enumerate}

\hline
Multi-SLAM & Build one shared map of the house from many robots. \\

\vspace{0.8em}
\textbf{What we are actually doing:} map the house $\rightarrow$ know
positions $\rightarrow$ split the jobs $\rightarrow$ plan conflict-free
traffic $\rightarrow$ drive until every place is done.

\section{Things to say in a demo (optional talking points)}
%------------------------------------------------------------------------------

\begin{itemize}[leftmargin=*]
  \item ``CBBA is the team manager; MAPF is the traffic controller; low-level
        driving is just following the green light.''
  \item ``We are not using the fancy CBS/ECBS planners here --- we use a
        priority order so planning stays quick.''
  \item ``If you see robots pause, that can be intentional waiting so someone
        else can pass.''
  \item ``Assignment happens before motion; timeouts during assignment are
        usually about scoring routes, not about driving failure.''
\end{itemize}
